# Decisiones de arquitectura (ADR ligero)

> Cada decisión se registra con su contexto y trade-off. Esto alimenta directamente la memoria del TFM.
> Formato: **Decisión — Motivo — Alternativas descartadas.**

## Cerradas

| # | Decisión | Motivo | Alternativas descartadas |
|---|---|---|---|
| D-01 | Orquestación con **LangGraph.js** | Estado nativo entre iteraciones, bucles condicionales e `interrupt` para human-in-the-loop | Llamadas directas a la API de OpenAI; LangChain solo; n8n |
| D-02 | Backend en **Node.js + TypeScript** | Es la tecnología que mejor conoce la autora; evita curva extra | Python (más natural para LangGraph, pero curva adicional) |
| D-03 | Jira vía **MCP oficial de Atlassian (Rovo)** | Reduce complejidad y tiempo; prioriza robustez del conector oficial. Trade-off consciente frente al valor académico de construirlo | MCP propio para Jira |
| D-04 | MCP **propio** solo para Jenkins (fase posterior) | No hay alternativa oficial equivalente; aquí sí aporta valor de diseño | — |
| D-05 | **PostgreSQL** para todo el modelo | Compatibilidad futura con pgvector, evita una segunda BBDD | Mongo, vector DB dedicada |
| D-06 | **Polling** para estado en tiempo real | Simplicidad en MVP | WebSockets / SSE (evolución posible) |
| D-07 | Runner Robot Framework en **contenedor Docker independiente** | Aislamiento y no mezclar Python en Node; Vercel no sirve para procesos largos | Importar Python desde Node |
| D-08 | Frontend en **Vercel**, backend en **contenedor** | Vercel resuelve Next.js; el backend necesita Docker y timeouts largos | Todo serverless |

| D-18 | **Frontend con ESLint 9**, backend con ESLint 10 | `eslint-plugin-react` (vía `eslint-config-next@16`) usa `context.getFilename()`, eliminado en ESLint 10. Revisar al actualizar `eslint-config-next` | Frontend en ESLint 10 (rompe el lint) |
| D-19 | **`main` protegida** en GitHub: PR obligatorio antes de mergear, sin force push | Cumple el flujo de ramas de `05-convenciones.md`. Con una sola persona se exigen 0 aprobaciones (no se puede aprobar el propio PR) | Push directo a `main` |
| D-20 | `next`, `react` y `react-dom` se instalan en `frontend` desde la Fase 0 | `eslint-config-next` carga un parser que vive dentro de `next`; sin él el lint del frontend falla | Excluir el frontend del lint hasta la Fase 4 (dejaba la config sin validar) |
| D-21 | Umbral de "mismo error" (US-10): **2 intentos seguidos** fallando por el mismo motivo ⇒ se considera falta de información. Valor configurable | Punto de partida simple; se ajusta con casos reales en la Fase 1 | 3 intentos (gasta más intentos y tokens antes de preguntar); similitud semántica (más complejo) |
| D-22 | **Límite de tokens por job** además del máximo de intentos (TS-02), configurable | Barato de implementar; protege el gasto aunque el límite de intentos falle | Solo límite de intentos |
| D-23 | En Jira se muestran **mensajes distintos para 404 y 403** (US-04) | App interna con usuarios autenticados: el riesgo de confirmar que una US existe es bajo y el mensaje distinto es más útil | Mismo mensaje para ambos |

| D-27 | Prioridades MoSCoW de `06-user-stories.md` confirmadas (Should: US-09, US-12, TS-02, TS-04) | Coherentes con el walking skeleton: el MVP sobrevive sin ellas si el tiempo aprieta | — |
| D-28 | **Intento = una ejecución** del test. Máximo 5 ejecuciones por job (la generación inicial es el intento 1, hasta 4 correcciones) | Definición simple y medible; el límite se comprueba antes de cada ejecución | 1 generación + 5 correcciones |
| D-29 | LLM mediante el **SDK oficial `openai`** detrás de un `LlmPort` | Se aprende la API directamente (structured outputs, tokens, errores) y el puerto permite añadir luego un adaptador `@langchain/openai` y comparar | `@langchain/openai` desde el inicio (más abstracción, menos visibilidad) |
| D-30 | El grafo depende de **puertos** (`LlmPort`, `RunnerPort`), nunca de OpenAI o Docker. Los tests usan dobles (`FakeLlm`, `FakeRunner`) | Tests deterministas, CI sin llamadas reales al LLM (TS-04.3) | Dependencias directas en los nodos |
| D-31 | `clasificar_fallo` se divide en una **regla determinista** (mismo error normalizado en 2 intentos seguidos ⇒ falta de info) y un **triage con LLM** con salida estructurada para el resto | La parte determinista se testea sin gastar tokens; el LLM solo decide los casos difusos | Clasificar todo con el LLM |
| D-32 | `interrupt` de LangGraph con **checkpointer en memoria** en la Fase 1; en la Fase 3 pasa a Postgres | Permite validar el flujo de aclaración sin BBDD todavía | Persistencia desde la Fase 1 |
| D-33 | **Tests unitarios junto al código** (`x.ts` + `x.test.ts`) y dobles en `src/agent/testing/`. Los tests de integración (API + Postgres, Fase 3) irán en `backend/tests/integration/`. Al crear el Dockerfile se añadirá un `tsconfig.build.json` que excluya `*.test.ts` y `testing/` del `dist/` | Es lo más cómodo con Vitest y evita mantener una estructura espejo; los tests lentos con infraestructura sí merecen carpeta y ejecución propias | Carpeta `tests/` espejo para todo |
| D-34 | Los tests generados usan **Browser Library (Playwright)** | Esperas automáticas: menos fallos falsos por tiempos, que son los que más intentos (y tokens) gastarían; es el estándar emergente en Robot Framework | SeleniumLibrary (más veterana; ver decisión abierta de soporte a proyectos Selenium) |
| D-35 | El `rf-runner` se basa en la **imagen oficial `marketsquare/robotframework-browser` con versión fija (20.6.0)**, ejecutada como `pwuser` | Trae Python, Robot, Playwright y navegadores ya integrados y probados; correr como no-root es requisito de la imagen y del aislamiento. Versión fija para reproducibilidad | Montar Playwright a mano sobre `python:slim` (más trabajo y más fallos); usar `latest` (cambia sin avisar) |
| D-36 | El runner usa `--shm-size=512m` (no `--ipc=host`), `--security-opt=no-new-privileges`, `--user pwuser`, y lanza `robot` sin pasar por una shell. Verificado con Chromium real | `--ipc=host` comparte memoria con el anfitrión y rompe el aislamiento; `--shm-size` da a Chromium lo que necesita sin esa apertura. Argumentos como lista (sin shell) evitan inyección de comandos | `--ipc=host` (recomendación de la imagen); `bash -c "..."` |
| D-37 | Dos modelos de OpenAI por variable de entorno: `OPENAI_MODEL_GENERATE=gpt-6.1-sol` para generar/corregir y `OPENAI_MODEL_TRIAGE=gpt-6-luna` para preguntas de aclaración y triaje. Adaptador sobre la **Responses API** | Sol da casi la calidad de Astra por ~1/5 del coste (≈0,07 USD vs ≈0,36 USD por ciclo de 20k tokens, a precios de la doc de oct-2026); Luna cuesta ≈0,004 USD en tareas cortas. Responses es la API recomendada para proyectos nuevos | Astra para todo (5× más caro sin necesidad demostrada); un solo modelo; Chat Completions (API heredada) |
| D-38 | Se amplía D-21: "mismo error dos veces ⇒ preguntar" solo aplica a fallos que **no** son de entorno ni errores de código. Nuevo tipo `environment` (`net::ERR_*`, `page.goto: Timeout`, `ECONNREFUSED`, timeout global del runner): **sin LLM y sin preguntar**; el 1.º se reintenta con el mismo test, **dos seguidos abortan** el job con `failureReason`. Cada reintento cuenta como intento (D-28). Los errores de código (keyword inexistente, sintaxis, librería mal importada, respuesta vacía del LLM) se corrigen aunque se repitan | Preguntar al usuario por una web caída no arregla nada y gasta su atención; "corregir" código por un fallo de entorno gasta tokens sin resultado. Un timeout esperando un **selector** no es de entorno (el selector puede estar mal), por eso solo se miran los de navegación | Tratar todo "timeout" como entorno (esconde selectores mal); que el LLM clasifique siempre (D-31, coste y variabilidad); reintento gratis que no cuente como intento (permite bucles infinitos) |
| D-39 | **PASS = código de salida 0 Y resumen de Robot con ≥1 test pasado, 0 fallidos y 0 omitidos.** Sin resumen que lo confirme, es FAIL. El prompt además prohíbe `Skip`/`Skip If`/`Pass Execution` | En la prueba `ambiguous` (Fase 1, paso 4) el modelo hizo que el test se omitiera con `Skip` por falta de credenciales y el runner lo dio por PASS porque Robot sale con 0 si algo se omite. Un test omitido no ha verificado nada: el agente habría reportado éxito falso | Mirar solo el código de salida (falso PASS); usar `--skiponfailure` (no aplica); prohibirlo solo en el prompt (el LLM puede ignorarlo, la comprobación debe ser determinista) |
| D-40 | Nodo **`checkStory` al inicio del grafo**: el modelo barato (`triage`) lee solo el texto de la US y responde JSON (`{"ready":true}` o `{"ready":false,"question":"..."}`) validado con `zod`. Si falta información se pausa en `askClarification` **antes de generar**; tras la respuesta no se vuelve a comprobar. Fail-open: si la respuesta no es válida, se da la US por lista. Se desactiva con `STORY_CHECK=false` | En la prueba `ambiguous` el agente gastó 4 ejecuciones inventando una interfaz y nunca preguntó (los fallos eran distintos, la regla de "mismo error" no saltó). Preguntar antes cuesta una llamada barata y evita intentos inútiles. **Límite conocido**: solo ve la US, no la web, así que no detecta "la US pide una función que la app no tiene"; eso solo se ve tras ejecutar (triage con LLM, D-31) | Triage con LLM tras cada fallo (D-31; sigue pendiente como red de seguridad); dar la página al modelo (más coste y complejidad); fail-closed (bloquea al usuario si el validador falla) |
| D-41 | Al **corregir**, el modelo puede responder `NEEDS_INFO: <pregunta>` en vez de código (solo si los logs muestran que falta información o que la función no existe en la app). `parseNeedsInfo` lo reconoce solo al principio de la respuesta; el intento pasa a `missing_info` y el grafo pausa en `askClarification` (arista `routeAfterFix`). El prompt de corrección define dos salidas explícitas, sin la regla "responde SOLO con el .robot" | En `ambiguous` el agente gastó 5 ejecuciones (12.312 tokens) aunque desde la 2.ª el propio test decía que la web no tiene perfil ni baja; los mensajes cambiaban de redacción y `isRepeatedError` no saltaba. El modelo ya tiene los logs delante al corregir, así que decidir ahí no cuesta ninguna llamada extra | Triage con LLM tras cada fallo (D-31: una llamada más por fallo; sigue como red de seguridad si D falla con datos reales); comparar logs por similitud difusa (frágil). Riesgo conocido: que el modelo se rinda pronto con NEEDS_INFO; se limita en el prompt y se vigila con las pruebas reales |
| D-42 | **(Implementada y validada con el modelo real, 2026-10-15)** Dos salidas limpias para una US que no se puede cumplir: (1) **límite de rondas de aclaración** configurable (p. ej. `MAX_CLARIFICATIONS=3`): al superarlo el job termina en `fail` con motivo "demasiadas aclaraciones sin resolver"; (2) tercera salida del modelo al corregir, **`CANNOT_TEST: <motivo>`**, para cuando la función no existe en la aplicación y el usuario ya lo ha confirmado: el job termina en `fail` con ese motivo en `failureReason`, sin volver a preguntar. Misma mecánica que D-41 (lector puro + arista tras `fixTest` + tests). Detalles de diseño: `CANNOT_TEST` solo cierra el job si el usuario ya contestó alguna aclaración (antes de eso se trata como pregunta, con su motivo como texto); las rondas se cuentan por los mensajes del agente en `clarifications`, sin contador aparte que se desincronice; `markFailed` deduce el motivo (`failureReason`, o límite de rondas si quedaba una pregunta pendiente). Resultado real: `ambiguous` pasó de 12.312 tokens y `fail` sin explicación a 4.968 tokens y `fail` con motivo; `pass` (594) y `fix` (731) siguen pasando sin preguntar | En la prueba `ambiguous` con D-41, tras decirle al agente que la web no tiene la función, generó otro test, falló y volvió a preguntar ("¿puedes proporcionar una aplicación donde esté implementada?"): un callejón sin salida, porque la URL es configuración del proyecto y no se responde desde el chat. Además cada respuesta reinicia el contador de intentos (D-14), así que hoy solo el límite de tokens frena un bucle de preguntas | Solo el límite de rondas (protege el coste pero no explica el motivo al usuario); solo `CANNOT_TEST` (depende de que el modelo acierte); permitir cambiar la URL desde el chat (fuera del alcance del MVP, RNF-6 la fija a nivel de proyecto) |
| D-43 | **Estrategia tras la Fase 1: "Camino A adelgazado".** Se mantiene el orden del plan (Fase 2 Jira → Fase 3 API+BD → Fase 4 Frontend) pero cada fase se hace **mínima y con tests**, sin pulir antes de tener el esqueleto completo. La Fase 2 se reduce a buscar una US por su ID y devolver un error claro si no existe o no hay permisos (US-03 y US-04), con un **token de desarrollo fijo**; el login por usuario con Atlassian queda para la Fase 5. La seguridad fuerte (login, roles, red del contenedor, auditoría de dependencias) llega en su fase | Se quiere ver algo funcionando de extremo a extremo cuanto antes (walking skeleton, hito de la Fase 4) sin posponer la integración con Jira, que es lo que hace único el TFM y la parte con más incertidumbre. Los cimientos de seguridad ya están (secretos fuera del código, aislamiento del runner, datos no confiables entre etiquetas) | **Camino B**: API+BD y frontend primero con la US pegada a mano y Jira después (demo antes, pero se aplaza la parte de mayor riesgo); construir toda la seguridad antes del frontend (nada visible durante mucho tiempo) |
| D-44 | **El MVP es de una sola empresa (single-tenant)**: se desarrolla y valida con la instancia de Atlassian de YourAutoQA. Ofrecerlo a otras empresas es una **fase futura (Fase 10)**, a plantear cuando todo esté en producción. En principio, **un despliegue por empresa** (cada una con su propia instancia de Atlassian, URL de la aplicación bajo test y credenciales en su entorno); la alternativa **SaaS multiempresa** (un solo despliegue, `tenant_id` en las tablas, `cloudId` por empresa, OAuth por usuario) se decide entonces | Los requisitos y las historias no piden multiempresa (solo RNF-6, URL de la aplicación por proyecto), y `CLAUDE.md` pide no inventar requisitos. Con un despliegue por empresa, un token o cuenta de servicio de Atlassian es viable porque el secreto vive en el propio entorno de esa empresa; en un SaaS, custodiar una clave por cliente sería un riesgo serio. Con MCP, cada llamada consume créditos de Rovo de la organización que la hace (dato comercial a valorar). `JiraPort` tendrá que recibir en el futuro a qué empresa y con qué usuario se consulta (cambio localizado gracias al puerto) | Diseñar ya como SaaS multiempresa (mucho más trabajo antes de tener un esqueleto que funcione, contra D-43). Pendiente de valorar en la Fase 3: si añadir `tenant_id` a las tablas desde el principio, que es barato ahora y caro después |
| D-45 | **Lectura de la US por la API REST de Jira, no por el MCP de Atlassian (spike del 2026-10-25).** `JiraPort` se implementa con un adaptador REST que llama a `https://api.atlassian.com/ex/jira/<cloudId>/rest/api/3/issue/<clave>` con `Authorization: Basic email:token`, usando un **token con ámbitos que solo tiene `read:jira-work`** (sin dependencias nuevas: `fetch` de Node 22). La descripción llega en **ADF** (JSON en árbol), así que se añade un conversor ADF → texto puro y testeado; `splitAcceptanceCriteria` sigue igual. Jira devuelve **404 tanto si la incidencia no existe como si no se puede ver**, así que `not_found` cubre ambos casos y `forbidden` queda para 401/403 reales; el mensaje viene localizado y no se usa, solo el código HTTP. Configuración: `ATLASSIAN_EMAIL`, `ATLASSIAN_API_TOKEN`, `ATLASSIAN_CLOUD_ID` (el `cloudId` no es secreto y se obtiene de `https://<sitio>/_edge/tenant_info`). El MCP queda como alternativa futura tras el mismo puerto | Con el MCP v2 y un token de API con ámbitos (`read`/`search:jira:agent-interface` y `read:me`), la conexión y `atlassianUserInfo` funcionan, pero **todas las herramientas de Jira devuelven 401 "Failed to fetch accessible products"**, con UUID o URL como `cloudId`, y la consulta equivalente `accessible-resources` también da 401. No se encontró el error en la documentación ni en los foros; parece un fallo o limitación de Atlassian (se reporta como issue en `atlassian/atlassian-mcp-server`). La API REST con un solo ámbito de lectura es más simple, más fiable, de mínimo privilegio y suficiente para US-03 y US-04. Gracias a `JiraPort` el cambio no toca el agente | Seguir insistiendo con el MCP (incierto y fuera de nuestro control); token sin ámbitos con la API REST (acceso total a la cuenta, contra el mínimo privilegio); OAuth 2.1 en la Fase 2 (necesita login de usuario, que llega en la Fase 5). Se mantiene la intención de D-43 de usar el MCP en producción cuando funcione con el login de cada usuario |
| D-46 | **API HTTP con Express 5, probada con `supertest`.** `createApp(deps)` crea la aplicación sin abrir ningún puerto y las rutas son una capa fina sobre un `JobService`: la lógica (leer la US, crear el job, lanzar el grafo) vive en el servicio y en puertos como `JobRepository`, no en las rutas. `POST /jobs` lee la US de Jira **antes** de crear el job (es rápido y síncrono): si falla, responde con el error (400 `invalid_key`, 404 `not_found`, 403 `forbidden`, 502 `unavailable`, cuerpo `{ "error": { "code", "message" } }`) y no crea nada; si va bien, responde 202 con el id y el grafo corre en segundo plano (RNF-3) con `thread_id` = id del job. | Express es el estándar de Node que más se encuentra en el mercado y el que el plan ya contemplaba; la ventaja de Fastify (`inject`) es pequeña y `supertest` la cubre. Con el framework como capa fina, cambiarlo luego cuesta poco. Validar antes de crear el job cumple US-04.3 y US-04.4 sin estados intermedios raros | Fastify (tests y esquemas de serie, pero menos extendido: pesó más aprender lo que más se usa); NestJS (demasiada estructura para un MVP); crear el job primero y leer Jira dentro del segundo plano (el usuario no vería el error al instante y quedarían jobs fallidos por claves que no existen) |
| D-47 | **Acceso a PostgreSQL con `pg` y SQL escrito a mano, con migraciones numeradas en archivos `.sql`.** `PostgresJobRepository` implementa `JobRepository` y debe pasar los mismos tests que `InMemoryJobRepository`, ejecutados contra una Postgres real. Postgres local con `docker-compose.yml` (imagen `postgres:17`, puerto solo en `127.0.0.1`, volumen para que los datos sobrevivan a un reinicio). | Con 2 o 3 tablas, escribir el SQL es poco código y se ve exactamente qué consulta se lanza (más fácil de explicar en la memoria y de depurar); evita aprender y mantener un ORM y su generador de tipos. El puerto `JobRepository` aísla el resto del sistema, así que pasar a un ORM más adelante sería un cambio localizado | Drizzle (buena opción si el SQL a mano se vuelve pesado: tipos generados y migraciones integradas); Prisma (más magia y un paso de generación, menos transparente para el TFM); imagen con `pgvector` desde ya (no hace falta hasta la Fase 8; cambiar de imagen entonces es sencillo) |
| D-48 | **Frontend con Next.js (App Router) probado con Vitest + Testing Library.** Los componentes reciben sus dependencias por **props** (`loadJobs`, `createJob`, `clarify`, `loadJob`) con la función real como valor por defecto, en vez de simular módulos. Next reenvía `/api/*` al backend (`rewrites`, variable `BACKEND_URL`, por defecto `http://localhost:3000`) y corre en el puerto 3001 | Mismo patrón de puertos que el backend (D-30): los tests no necesitan red ni mocks de módulos y fijan lo que ve una persona (roles, etiquetas). Con el proxy el navegador solo habla con un origen: sin CORS y, en la etapa de login, la cookie de sesión será del mismo origen | `vi.mock` de módulos (más frágil); llamar al backend directamente desde el navegador (CORS y cookies entre orígenes) |
| D-49 | La **tira de intentos de la lista se deduce** del resumen (`GET /jobs` solo da `attemptCount`): como el agente solo reintenta cuando falla, todos los intentos terminados fallaron salvo el último de un job `done`. El **detalle usa los resultados reales** (`GET /jobs/:id`) | Evita pagar el peso de intentos y logs en la lista y no obliga a tocar el backend. Si algún día difieren, manda el detalle | Ampliar `GET /jobs` con el resultado de cada intento (más datos por fila) |
| D-50 | **Refresco por polling cada 3 s (`pollIntervalMs`, configurable) solo mientras algún job esté `generating` o `running`.** Cada consulta programa la siguiente al terminar (sin `setInterval`, así nunca se solapan dos peticiones). La regla es `shouldPoll`, que lista los estados **activos**: un estado desconocido no se consulta | Concreta D-06 (polling) y cumple RNF-3 sin gastar peticiones con jobs parados. `awaiting_clarification` no se consulta: el agente espera a una persona, y al contestar se recarga | `setInterval` fijo (solapa peticiones y consulta siempre); listar los estados parados (un estado nuevo martillearía al servidor) |
| D-51 | **Aclaración en el detalle del job**: la pregunta pendiente y una caja de respuesta con aviso de **usar solo credenciales de prueba**, contador y límite de 2000 caracteres (el mismo que el backend, hoy duplicado). El backend solo guarda la **pregunta actual**, no el histórico de preguntas y respuestas, así que no hay conversación completa | La respuesta acaba en el prompt del LLM (entrada no confiable, TS-01) y gasta tokens; el aviso evita que se peguen contraseñas reales. Mostrar el histórico exigiría ampliar la API | Chat con histórico (requiere guardar y exponer los mensajes de `clarifications`) |
| D-52 | **Diseño visual** (generado con la skill UI/UX Pro Max): tema **oscuro por defecto** (estilo "Dark Mode OLED") y claro si el sistema lo pide, tipografías Fira Sans y Fira Code, tokens de color en variables CSS y estados siempre con **color, glifo y texto**. Sustituye a la propuesta inicial (claro, Instrument Sans) | Es una herramienta técnica para leer logs y código; el contraste se verifica en ambos temas | Propuesta inicial (tema claro con Instrument Sans) |
| D-53 | **Login con Atlassian dentro de Express** (`backend/src/auth`, rutas `/auth/login`, `/callback`, `/logout`, `/me`), OAuth 2.0 (3LO) con **un solo ámbito, `read:me`** (solo identidad; Jira sigue leyéndose con el token de API de D-45). App de Atlassian de tipo **Resource-level**, callback `http://localhost:3001/api/auth/callback` (entra por Next y Next reenvía `/api/*`, así la cookie es del mismo origen). El `client secret` solo vive en `.env`. Idea para después: vincular Jira por usuario pidiendo `read:jira-work` y `offline_access` | Cumple la decisión de no usar NextAuth y mantiene mínimo privilegio: el login no necesita acceso a datos de Jira | NextAuth/Auth0/Clerk; pedir ya los ámbitos de Jira |
| D-54 | **Modelo de datos de identidad** (migración `002`): `users` (rol con `CHECK`, por defecto `QA Executer`, D-25), `linked_accounts` (clave `(provider, provider_account_id)`, para sumar Google sin tocar `users`), `sessions` y `jobs.user_id` **nullable** (los jobs anteriores al login no tienen dueño; `ON DELETE SET NULL`). El primer login crea usuario + cuenta vinculada en una transacción; los siguientes solo refrescan nombre, email y avatar y **nunca tocan el rol** | Separar usuario y cuenta es el diseño pedido en US-01 (nota). Respetar el rol evita que un login "deshaga" lo que decidió un Admin | Columna `atlassian_id` dentro de `users` |
| D-55 | **Sesiones en servidor, no JWT**: cookie `yaqa_session` `httpOnly`, `SameSite=Lax`, `Secure` si `COOKIE_SECURE=true`, con un token de 256 bits aleatorios; en Postgres solo se guarda su **hash SHA-256**. Caduca a las `SESSION_TTL_HOURS` (12 por defecto). El rol se lee de la BD en cada petición | Se puede revocar al momento (logout, cambio de rol) y robar la tabla no sirve para entrar. SHA-256 basta porque el token ya es aleatorio (no hace falta bcrypt) | JWT firmado (no revocable sin lista); sesión en memoria |
| D-56 | **Anti-CSRF del login**: el `state` aleatorio viaja a Atlassian y a una cookie `httpOnly` de 10 min; el callback lo compara y la borra. Los fallos vuelven a `/login?error=state\|cancelled\|failed` (US-01.4). **Logout por `POST`** (un `GET` se podría disparar desde una imagen de otra web) | Impide que alguien nos cuele un login que no empezó este navegador | Sin `state`; logout por `GET` |
| D-57 | **Permisos por acción**, no por ruta: la matriz de US-02 es una sola tabla (`ROLES` y `can(rol, acción)` en `auth/roles.ts`) y cada ruta declara `requirePermission('job:create')`. **401** = sin sesión o caducada, **403** = sesión válida pero rol insuficiente, y en ese caso no se llama a Jira ni se crea nada (US-02.5). `GET /auth/me` devuelve usuario y `permissions` para que la interfaz sepa qué mostrar, pero el backend lo vuelve a comprobar | Un solo sitio donde cambiar permisos; la interfaz nunca es la barrera de seguridad | Comprobar `if (role === ...)` en cada ruta |
| D-58 | **Atlassian como puerto** (`AtlassianOAuthPort`): la implementación real usa `fetch` inyectable y los tests un `FakeAtlassian`, así ningún test llama a Atlassian. Los errores se reducen a `AuthError` con mensaje propio (nunca el texto de Atlassian ni el secreto) | Igual que `JiraPort` y `LlmPort`: tests deterministas y sin red | Mockear `fetch` global |
| D-59 | **Administración mínima** (US-12, versión simple): `GET /admin/users` y `PATCH /admin/users/:id/role`, solo Admin. Un Admin **no puede cambiarse su propio rol** (409) para no dejar la app sin Admins. El rol que Atlassian no cubre (email oculto) queda con email vacío | Es lo mínimo para poder subir de rol a alguien sin tocar la base de datos a mano | Cambiar roles solo por SQL |
| D-60 | **Quién entra como Admin la primera vez**: los correos de `ADMIN_EMAILS` (comparados en minúsculas; un email vacío nunca coincide). Solo se aplica al crear el usuario; después manda lo que decida un Admin. `ADMIN_EMAILS` es **del despliegue** (una empresa, D-44); en el SaaS multiempresa de la Fase 10 se sustituirá por "quien registra la empresa es su Admin". Mejora futura: al vincular Jira por usuario, los administradores del sitio de Jira podrían entrar como Admin (hoy no se puede saber con el ámbito `read:me`) | D-25 deja a todos como QA Executer y sin esta regla nadie podría subir el rol de los demás. Una lista explícita es más segura que "el primero que llegue" en un servidor expuesto | El primer usuario de la BD es Admin; ser administrador de Jira |
| D-61 | **Control de acceso en el frontend en tres capas**: `proxy.ts` (Next 16) manda a `/login` si falta la cookie de sesión, sin destello de contenido (US-01.1); `AuthProvider` pide `/auth/me` y, si el backend responde 401 en cualquier petición, lleva a `/login?error=expired` (US-01.5); los componentes ocultan lo que el rol no puede hacer según `permissions` (US-02.1, p. ej. sin `job:create` no hay formulario). Ninguna capa es seguridad: la barrera real es el 403 del backend (D-57) | Buena experiencia sin confiar en el navegador | Solo ocultar botones; validar la sesión en el proxy (obliga a que Next llame al backend en cada navegación) |
